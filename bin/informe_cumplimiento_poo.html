Resumen Ejecutivo: El presente proyecto integra de manera coherente y funcional los pilares fundamentales de la POO (Abstracción, Encapsulamiento, Herencia y Polimorfismo), junto con interfaces, colecciones genéricas (ArrayList), interacción por consola con Scanner, sobrecarga de constructores y un sistema de menús jerárquico por roles. Todas las clases están vinculadas por relaciones de negocio sólidas, evitando clases aisladas.

1. Contexto del Problema y Arquitectura del Sistema

El sistema DocuGestión 2 aborda la problemática de control logístico y documental en una distribuidora comercial. La solución se organiza en dos dominios integrados:

  • Dominio de Recursos Humanos y Seguridad: Modela las entidades de personas físicas (Persona), trabajadores con rol operativo/administrativo y salarial (Trabajador), y usuarios con credenciales de acceso para autenticación por roles (Usuarios).
  • Dominio Documental y Operativo: Modela documentos mercantiles (Documento), remitos con detalle de mercadería despachada (Remito) y despachos logísticos de entrega (Despacho) asociados a remitos y operarios.

3. Análisis Detallado de Puntos Clave

3.1. Estructura Mínima Solicitada

  1. Clase Padre: Persona (clase abstracta con datos generales de identidad).
  2. Clase Hija: Trabajador (incorpora identidad laboral, cargo y salario mediante modificadores protected).
  3. Clase Nieta: Usuarios (incorpora credenciales de seguridad para el inicio de sesión y autenticación en el sistema).
  4. Clases Relacionadas por Composición: Despacho compone a Remito; a su vez Remito compone una colección de Detalle, que compone a Producto.
  5. Clase Principal con main(): app.Main, la cual inicia el control de sesiones con hasta 3 intentos de login y delega en el menú principal según el rol.

3.2. Implementación de Interfaces y Polimorfismo

Para satisfacer la consigna con el máximo rigor académico, se creó la interfaz Imprimible: 

package logica;

public interface Imprimible {
    void mostrarInformacion();
    String obtenerResumen();
}

Tanto Documento como Persona implementan este contrato. En DespachoCrud.java se diseñó el método listarHistorialDocumentos() que demuestra el polimorfismo puro: 

// Colección polimórfica basada en la superclase abstracta
List<Documento> documentos = new ArrayList<>();
for (Despacho d : despachos) {
    documentos.add(d.getRemito()); // Agrega un Remito
    documentos.add(d);             // Agrega un Despacho
}

// Invocación polimórfica resuelta en tiempo de ejecución (Late Binding)
for (Documento doc : documentos) {
    System.out.println("Resumen: " + doc.obtenerResumen()); // Ligadura de interfaz
    doc.mostrarInformacion();                              // Ligadura de clase abstracta
}

3.3. Integración de `Producto`, `Detalle` y Sobrecarga de Constructores

En la carga interactiva de despachos (DespachoCrud.crearDespacho()), el sistema solicita al usuario cargar productos para el remito, aplicando la sobrecarga de constructores de Producto según los datos provistos: 

// Demostración práctica de sobrecarga de constructores
Producto producto;
if (cant > 0) {
    producto = new Producto(cod, nom, cant); // Constructor de 3 parámetros
} else {
    producto = new Producto(cod, nom);       // Constructor sobrecargado de 2 parámetros
}
remito.agregarProducto(producto);            // Demostración de composición

4. Guía Estratégica para la Defensa Oral

P: ¿Por qué Persona y Documento son clases abstractas?
R: Porque en nuestro modelo de negocio no existen "personas genéricas" ni "documentos genéricos" en el plano real; siempre son trabajadores/usuarios específicos o remitos/despachos concretos. Su rol es servir de superclase base para reutilizar atributos y obligar a las clases hijas a implementar el método abstracto mostrarInformacion().
P: ¿Cuál es la diferencia entre la Herencia de Persona y la Composición de Remito con Detalle?
R: La herencia responde a la relación "es un" (un Trabajador es una Persona). La composición responde a la relación "tiene un" o "parte de" (un Remito tiene detalles de producto, y si se destruye el remito, sus detalles carecen de sentido individual).
P: ¿Dónde se comprueba el uso de modificadores protected?
R: En Trabajador.java y Documento.java. Los atributos como cargo, salario y id_trabajador están protegidos para que la clase nieta Usuarios acceda a ellos directamente sin violar el encapsulamiento hacia clases externas.
P: ¿Por qué la lista de usuarios y el Scanner son static?
R: La lista usuariosRegistrados en Usuarios.java es estática para que todas las instancias compartan el mismo registro de autenticación en memoria. El Scanner en Utiles.java es estático para centralizar el flujo de entrada estándar System.in y evitar conflictos de múltiples lectores abiertos.
